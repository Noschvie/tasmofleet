# Custom firmware upload security notes (M2-8, part A)

Code: `internal/firmware/custom.go` (checks, storage, minimal borrowing), `internal/web/firmware_custom.go` (route, audit), the multipart entry in `internal/app/guard.go`, migration `0014_firmware_custom.sql`. Spec §8.6.

An uploaded image is a normal cache artifact with source `custom`. It reaches a device only through the same path as an upstream file: `fwselect.Select`, `Plan`, `Guard` (immediately before `OtaUrl` and `Upgrade`), the device-facing firmware server. Nothing in that path knows about "custom", so no rule is relaxed.

## Threats and rules

| ID | Threat | Rule | Test |
| -- | ------ | ---- | ---- |
| C1 | Anyone but an admin plants firmware | `POST /firmware/custom` is admin only; operators and anonymous callers get 403/401 and nothing is stored. Operators do not see the form. No step-up (same as prefetch and delete; the image still needs a human to choose it for a device). | `TestCustomUploadIsAdminOnly`, e2e "operators see no upload form" |
| C2 | CSRF forces an upload | The CSRF token must be in the `X-CSRF-Token` header (HTMX sends it), so the CSRF middleware never parses the multipart body; a wrong token is 403, a missing header is 415. Cross-origin requests fail `CrossOriginProtection` as everywhere. | `TestGuardBodiesCustomFirmwareUploadNeedsHeaderTokenAndIsCapped` |
| C3 | Wrong chip: an ESP32 image reaches an ESP8266 (or the reverse) | The family comes from the image header (`fwselect.InspectImage` through `Options.Inspect`), never from the file name or the browser's content type. The stored name and container come from `fwselect.Select` for that family, so `Guard` rules 2, 3, 5, 6 and 7 hold unchanged. The update page offers the image to every device, but a device of another family fails in planning (`Select` asks for a file the release does not have) and again in `Guard`. | `TestAddCustomDetectsFamilyAndNormalisesContainer`, `TestGuardAppliesToCustomImages`, `TestITCustomImageNeverCrossesFamilies` |
| C4 | Safeboot, factory or full-flash image flashed as an OTA app | Refused when the upload's file name contains `safeboot`, `factory`, `bootloader` or `partition`, when the build is `safeboot`, and when the image has a partition table at flash offset 0x8000 (a full-flash image). Unknown chip ids, wrong magic, garbage, truncated or corrupt gzip and files under 1 KiB are refused. **Limit:** a safeboot app image has the same header as a normal one, so an uploader who renames it defeats the name check. The admin is trusted for content; the checks catch mistakes and obvious misuse. | `TestAddCustomRefusals` |
| C5 | Disk or memory exhaustion | Cap on the uncompressed image: 4 MiB (ESP8266) / 8 MiB (ESP32), constants `firmware.MaxCustomESP8266` / `MaxCustomESP32`; a gzip bomb stops at the cap. The request body is capped at `MaxCustomUpload` (8 MiB + 256 KiB) by the app guard and again in the handler. The file is streamed through the pipeline into a temp file, never held in memory. A refused upload leaves no file, directory or row. Only admins can upload; there is no count limit (an admin can fill the disk, as with prefetch). | `TestAddCustomRefusals` (oversize rows), `TestCustomUploadRefusalsAreAuditedAndStoreNothing` |
| C6 | Path traversal through names | The uploaded file name is display data only (`CleanFileName`: base name, no control characters, 128 runes) and never used in a path. The stored path is `custom/<key>/<release>/<name from Select>`; the release is validated as dotted digits (`validRelease`), the variant must be a build `Select` knows. Labels are free text (printable, 64 runes) and always HTML-escaped; they are not in paths or URLs. | `TestAddCustomIgnoresTheUploadedFileNameForThePath`, `TestAddCustomRefusals` (path rows), `TestCustomUploadListedOfferedAndAudited` |
| C7 | A custom image is mistaken for an upstream file of the same version (or the reverse) | Uploads may carry the version of an upstream release (a self-built 16.0.0). They are told apart by a key, the first 10 hex digits of the image's SHA-256, and never by version: `Artifact.Custom`, `Job.TargetCustom` and `Request.Custom` carry it. Devices fetch an upload at `/c/<key>/fw/<release>/<file>`, upstream files at `/fw/<release>/<file>`; `Lookup` and `FindArtifact` only return upstream rows, `LookupCustom`, `FindCustomArtifact` and `EnsureCustom` only uploads, and no code falls back from one to the other (a missing key is a 404 or a refusal, never the upstream file). The Guard is unchanged: it accepts the prefixed URL because it only requires the URL to end in `/fw/<release>/<file>`. The same bytes twice are refused. The store keeps `UNIQUE(release, filename)` and writes an upload's release column as `<key>~<release>` (`customPrefix`), removed again on read. | `TestCustomImageCoexistsWithUpstreamOfTheSameVersion`, `TestCustomArtifactCoexistsWithUpstreamOfTheSameReleaseAndName`, `TestEnsureKeepsUpstreamAndCustomApart`, `TestEnsureCustomWithoutSupportFailsClosed`, `TestRetryRequestKeepsTheCustomImage`, `TestITCustomAndUpstreamOfTheSameVersionAreServedApart`, `TestUpdateWithUnknownCustomKeyIsRefused` |
| C8 | The staged update has no minimal image | An ESP8266 custom release borrows a copy of the newest upstream `tasmota-minimal.bin.gz` (cached, or fetched through the normal download path with its size limit, cross-check and header check). The copy is re-hashed against its source and re-inspected; `Guard` checks it like any minimal stage. | `TestCustomReleaseGetsAMinimalImage`, `TestITCustomESP8266IsStagedViaMinimal` |
| C9 | Deleting an image a running job needs | `Manager.Delete` refuses while a queued or running job holds the image or its borrowed minimal copy, and when the lookup fails (fail closed), as for cached files. Deleting an image removes the minimal copy with it. "Delete unused" and `Prune` never touch uploads (they cannot be downloaded again). | `TestCustomDeleteAndRetention`, `TestCustomImageDeleteIsExplicitOnly` |
| C10 | No trace | Audit events: `firmware.custom.upload` (also refusals, with the reason; success carries release, file, family, label, original name, SHA-256, size), `firmware.custom.use` (the transaction that installs an upload, with label and SHA-256), `firmware.delete` (existing). Provenance (label, uploader, time, original name) is in `firmware_custom`. | `TestCustomUploadListedOfferedAndAudited`, `TestCustomUseIsAudited`, `TestCustomUploadRefusalsAreAuditedAndStoreNothing` |
| C11 | An upload becomes the default | Uploads are listed in their own option group on the update page, are never preselected, never "recommended", and `Latest`/`UpdateAvailable` only look at the upstream index. | `TestCustomUploadListedOfferedAndAudited` |

## Residual risks (accepted, homelab)

- The image content is trusted once it has the right chip and is not obviously a safeboot, factory or full-flash image. Tasmota images carry no signature we can check; the admin vouches for the file. The SHA-256 is recorded in the audit log and shown on the page.
- A safeboot app image uploaded under another file name passes the checks (C4).
- The form works with JavaScript only (HTMX), like the TasmoAdmin import.
- The 10-digit key is not a security boundary: it names a file, admins can upload, and a collision between two different images is refused as an upload error (negligible by chance).
- Development channel (Tasmota development builds as a source) is not part of this change.
