# Commands over MQTT: threat model and claims

Scope: how tasmofleet sends commands, reads, settings writes, policy fixes, backups, restores and the commands of a
firmware update to a device over its MQTT broker instead of its HTTP API (`internal/transport`, `internal/mqttcmd`,
`internal/backup`, `internal/restore`, `internal/ota`, spec 5.x, 6.5, 6.6 and 12.4). Findings are judged
against it: valid if they break a claim below or show a residual risk worse than stated.

> [!CAUTION]
> **Without an ACL on the broker, every MQTT client can read what TasmoFleet sends through it.** Commands, passwords
> typed into the console or a setting, and the whole configuration dump of every backed-up or restored device are
> delivered by the broker to every client that may subscribe to the device's topics (Home Assistant, Node-RED, MQTT
> Explorer, other devices). TasmoFleet cannot see whether the broker has an ACL, so it warns on every page where MQTT
> settings and MQTT-carried secrets appear (T18). Set one up: [broker ACL guide](../mqtt-broker-acl.md), which has a
> tested rule set and says plainly that the Mosquitto app of Home Assistant does not enforce an `acl_file` in version 7.1.3 (reported since 7.0.0).

## What changes compared with HTTP

- On the MQTT path only the broker protects the device (user, ACL, TLS). The device's web password
  plays no part; anyone who can publish to `cmnd/<topic>/#` can do what the console can do.
- Commands, settings writes and their replies travel through the broker. Since #605 every write of a device
  usable on TasmoFleet's broker goes there first, whatever it carries: a password (`WebPassword`, `MqttPassword`,
  `Password<n>`, `SSId<n>`, ...), a login inside a command (`OtaUrl http://user:pass@host/...`, `Sendmail`'s SMTP
  login), a change of the MQTT connection, a GPIO template. A secret is no reason for HTTP (the product owner's
  rule of 2026-11-14): on a usual Tasmota both ways are plain text. Tasmota serves no HTTPS, and TasmoFleet's HTTP
  call carries the command and the device's web password (HTTP Basic authentication) in clear; the device's leg to
  the broker is plain `tcp://` unless the firmware was built with TLS, so an `ssl://` URL on TasmoFleet's side does
  not protect the command on its way to the device. The difference: over HTTP a command goes from TasmoFleet to the
  device, over MQTT the broker delivers it, and the reply, to **every client subscribed to the device's topics**
  (`cmnd/<topic>/#`, `stat/<topic>/#`, `#`). Give the broker an ACL that lets only TasmoFleet and the device itself
  read and write a device's topics. A console or bulk command whose arguments the audit hides says so before it is
  sent (#826, T13); the pages that carry MQTT settings and MQTT-carried secrets show the broker ACL notice (#840, T18).
  TasmoFleet cannot tell whether the broker has an ACL and does not try.
- A command a person types whose arguments the audit hides (`cmdpolicy.ShownInFull`: it may carry a secret) names
  its transport in its confirmation, honestly, before anything is sent (#826, claim T13). Over MQTT: "The command goes
  to the device over the MQTT broker, unencrypted; the broker also delivers it to every client subscribed to this
  device's commands (a broker ACL prevents that)." With an `ssl://`, `tls://` or `mqtts://` broker URL "unencrypted"
  reads "encrypted from TasmoFleet to the broker" (TasmoFleet's leg only; the device's leg is plain on standard
  builds). Over HTTP: "The command goes to the device over HTTP, unencrypted." The bulk preview gives one row per
  transport with how many of the chosen devices take it. The console asks for every such command, also one that had
  no confirmation of its own before.
- What TasmoFleet shows and stores is masked as before, whatever the transport: the audit log and the console
  history hold only `cmdpolicy.Redacted` text, and replies pass `cmdpolicy.ScrubReply` (T7; command-policy L1, L2).

## Backups and restores over MQTT (#607)

Since #607 every backup (scheduled, before an update, manual, bulk, and the safety and check backups of a restore)
and every restore of a device usable on TasmoFleet's broker for a transfer goes over MQTT first, also while HTTP
works (claim T14). What crosses the broker then:

- **Backup** (`FileDownload` Type 2): the start `cmnd/<topic>/FileDownload {"Password":"<the device's MqttPassword>","Type":2}`
  carries the device's MQTT password in clear; then `FileDownload 0` (when the state of the topic is unknown) and one
  `?` per chunk. The replies on `stat/<topic>/FILEDOWNLOAD` carry the **whole settings dump** in base64: the Wi-Fi
  passwords, the web and MQTT passwords, tokens and keys. The `Status 1` to `Status 11` snapshot of the run follows
  the dump over MQTT.
- **Restore** (`FileUpload` Type 2): the start `{"Password":...,"Type":2,...}` with the device's MQTT password, the
  whole dump in base64 chunks on `cmnd/<topic>/FileUpload`, its MD5; before it `Status 5` (to every device on the
  topic, `DoAll`), the version and boot count reads, the MQTT settings the restore compares with the backup (R28:
  `Topic`, `Hostname` when the backup's Topic holds `%hostname%`, `Status 6` for MqttUser (#809), `MqttClient`, `Prefix`, `Status 3` for
  SetOption103 and SetOption132, `MqttFingerprint1/2`, and `MqttHost`/`MqttPort` when the inventory has no broker for
  the device; no password among them);
  and the safety and check backups as above.
- **Backup, files** (`UfsList` and `FileDownload` Type 8, #924), on a firmware built with `USE_UFILESYS_MQTT` and
  without an SD card: the listings, then per file a start `{"Password":"<the device's MqttPassword>","Type":8,"File":"<path>"}`
  (the password in clear once per file) and its chunks on `stat/<topic>/FILEDOWNLOAD`, which carry the **file
  contents**: Berry scripts with their tokens, `/tlskey` (the device's TLS private key), Zigbee data. A stock firmware
  answers the first file with Error 3 (its password crossed the broker once); its files go over HTTP as before.
- **Not over the broker:** the files a stock firmware or a device with an SD card holds, and every file a restore
  writes (see "What still uses HTTP"): they go over HTTP, to the device's address: read after a dump over MQTT only
  from a host that reports the device's MAC (`Status 5` over HTTP right before), written by a restore over MQTT after
  the same check (T15).

**Which password a transfer sends** (#609): `model.FilePassword`, the one mapping from a device's password mode to the
value: its own password (stored sealed), TasmoFleet's broker password (broker mode, resolved at send time), or the
empty password (the "No password" mode: Tasmota compares the `Password` with `strcmp`, so `""` matches an empty
`MqttPassword`). "Not set", broker mode without a broker password, or a value the start command cannot carry (a quote,
a backslash, a control character) send nothing: Choose names the reason and the transfer takes HTTP while it works.
A backup takes HTTP then only when the device answers there (#997, `transport.BackupPasswordBlocker`, asked by
`Router.backupNeedsPassword` right before `/dl`, also the `/dl` after a `FileDownload` that published nothing, on facts
decided again): HTTP failing counts as not reachable; HTTP not known to work (no
fresh answer on record) is settled by one `Status 11` over HTTP right then (`Router.httpAnswers`, the status timeout,
not the backup's download timeout), and a probe without an answer counts as not reachable; a fresh answer on record
keeps today's `/dl` without a probe. A device that is not reachable gets nothing: no `FileDownload`, no `/dl`, and the
backup ends at once with "Needs an MQTT password: ..." (what HTTP showed and why the password cannot be used, words
and dates only), the same for Back up now, Retry, a backup transaction and the scheduled run (counted as Failed, so it
stays in the failure notification), and for the backups before an update, of a template job and of Replace. A
device whose HTTP API is off (SetOption128 0) keeps the #447 rule, which is asked before this one: the scheduled run
skips it as "HTTP API off", Back up now and Retry refuse it with that reason, and a backup transaction does not attempt
it (decision Q2 of #997). The
Backups table, the device's Backups tab and the transaction's result row link the device's password form while the
cause holds (the same function on the live facts); with two or more such devices the Backups page links the Device MQTT
passwords card on System, MQTT. When HTTP carried a backup because MQTT could not and HTTP then fails, the error keeps
why MQTT could not (`Router.explainBackup`), and `errors.Is` still finds the HTTP error. A restore's safety backup is
pinned to the restore's transport (`internal/restore/flow.go`) and does not ask this rule: a restore takes HTTP only
while HTTP is not failing, so its safety backup over HTTP is not a backup into silence.
The restore's lockout check compares the backup's `MqttPassword` with the same value (R28). TasmoFleet takes the
password from the device's newest decoded backup (`mqtt_pwd`, in clear in the decoded JSON it already stores): after
every backup and in a pass over every device at each start, unless System, MQTT, "Take device passwords from backups" is off. That
talks to no device and puts nothing on the broker; the value is stored like a typed one, and the log and the audit
(`device.mqtt_password`, actor `system`) name only the mode, the source and the backup's date. The newer fact wins: a
backup replaces the stored password only when it was taken after the last save (the check is part of the store's
update). A backup's time is when the device's settings were read (the start of the dump, in whole seconds), so a
password saved after that read wins, however long the snapshot and the files step take. Only a run whose snapshot
shows one of the device's MACs (Status 5, read over the dump's transport) teaches: a dump over HTTP comes from
whatever host answers at the stored address, so a run from another host, without Status 5, or of a device without a
MAC in the inventory teaches nothing. A refusal (`Error 1`) is recorded only for the password that was sent, by the
dump, a file of the backup (Type 8), the settings upload and the test alike: when the stored one changed meanwhile,
nothing is marked (`store.MarkMQTTPasswordBadFor`). A backup taken after a refusal that shows the stored
password again ends the refusal mark, since the device holds that password. The edit form posts back the mode it
showed, so a save that leaves the select alone keeps a password learned while the form was open. A
replacement-hardware run is not the device's own and teaches nothing, and neither does an own newest run without a
decoded file.

**The password test** (#609, T23): `FileDownload {"Password":...,"Type":2}` to the device's topic, under the strict
rule of transfers. `Error 1` means refused (the device allocated nothing); `Started` means accepted, and
`FileDownload 0` follows at once, before any `?`. Tasmota answers that abort with one more data chunk of the dump
before `Aborted` (`CmndFileDownload` sends a chunk while its buffer is set, `xdrv_02_1_mqtt_file.ino` 16.0.0), so an
accepted test puts the password (in the start), the file header and one data chunk on the broker. That chunk is up to 2980 B on an
ESP8266 and 4480 B on an ESP32 ([research](../research/tasmota-mqtt-transport.md#2-filedownload-type-2-settings-dump),
lines 41-44), so it is most of the roughly 4096 B settings dump or all of it, with every password stored there (Wi-Fi,
web, `MqttPassword`), Tasmota-obfuscated only: close to the exposure of a whole backup over MQTT, which the ACL advice
below covers. Nothing is written to flash. HTTP cannot check the password (`Status 6` and the web UI mask it), so the
test has no HTTP path and adds no row to "What still uses HTTP".

Over HTTP the same dump is plain text too (Tasmota serves no HTTPS) with the web password beside it; the difference is
that the broker delivers a transfer to **every client subscribed to the device's topics** (`cmnd/<topic>/#`,
`stat/<topic>/#`, `#`). **Broker ACL advice:** what must not leak is *read*: the start command (with the MQTT
password) on `cmnd/<topic>/FileDownload` and `cmnd/<topic>/FileUpload`, the dump chunks on
`cmnd/<topic>/FileUpload` and `stat/<topic>/FILEDOWNLOAD`, and there too the chunks of every file a backup reads
over MQTT (#924; the private key `/tlskey` among them). Let only TasmoFleet's broker user and the devices read
`cmnd/#` and `stat/+/FILEDOWNLOAD`/`stat/+/FILEUPLOAD`; other clients (Home Assistant, Node-RED, loggers, MQTT
Explorer) may keep *writing* `cmnd/<topic>/...` and reading the `stat`, `tele` and discovery topics they use, but
none should read `#` or `cmnd/#`. TLS on TasmoFleet's leg (`mqtts://`) does not protect the device's leg on a
standard build. TasmoFleet never logs, shows or audits the password or the dump (T7, R24).

## Updates over MQTT (#608)

Since #608 the commands of a firmware update (`OtaUrl`, `Upgrade 1` and the job's reads between them: `Status 2`,
`Status 4`, `Status 11`, the bare `Upgrade`, the `OtaUrl` read, the INFO1 of the minimal and safeboot images) go over
MQTT whenever the device is usable there under the strict rule of writes, also while HTTP works (claim T5). The
image itself never crosses the broker: the device downloads it from TasmoFleet's firmware server over HTTP, as it
did before (Tasmota fetches the `OtaUrl` itself). What crosses the broker then:

- `OtaUrl <url>` with the whole firmware URL, a login in `FIRMWARE_BASE_URL` included, and Tasmota's reply on
  `stat/<topic>/RESULT`, which echoes the URL; `Upgrade 1` and its reply `Version X from <url>`. Over HTTP the same
  URL travels in clear in the request to the device; over MQTT the broker also delivers it to every client
  subscribed to the device's topics. TasmoFleet logs no command text; the job's own error texts (a URL the device
  stored or flashes that differs from the planned one) read the same over both transports.
- Not the device's passwords: an update needs no `MqttPassword` (it is no transfer).

The job keeps the path it chose at Submit for its whole life (D5, `Job.Transport`): a lost answer is probed over the
same path and never resent over the other (T3), and a pinned write is checked against the strict rule again right
before its publish (`Router.pinnedMQTT`, T6), so a topic another device may answer on since the pin (a scheduled
update planned hours earlier) gets no `OtaUrl` and no `Upgrade` and the job fails; on a topic marked as taken (T19)
its reads are refused too, so no identity read there is stored on the device. An update checks the device's family
and variant (Guard on the preflight identity, read over the job's own path), not its MAC: over MQTT the device's topic,
bound by the strict rule and the marks of T19, is what the update's identity rests on, as the address is over HTTP. `fwselect.Guard` runs right
before each `OtaUrl` and `Upgrade` on either path (safety rule 1). The backup before the update follows the backup's
own rule (T14), so it may go over HTTP while the update's commands go over MQTT. Push uploads stay HTTP while HTTP
works (see "Not yet moved"); `Upgrade` and `OtaUrl` typed in the console or sent as a bulk command keep their
transport (T13, the coordinator's decision of 2026-11-17).

## Residual risk

- **Low.** A broker client that spoofs a device topic can answer a query (a reply is matched by topic and by
  the command's key, not by a signature). A restore checks the MAC (`Status 5`, every reply heard before its
  upload); an update checks only family and variant (Guard on its preflight identity read over the job's path), no
  MAC, over either transport.
- **Low.** A write over MQTT first that the device did not confirm in time is an unknown outcome; the person sees it
  and decides (nothing resends it). Such a write, a switch of the power toggle included, marks the device like an
  unanswered read, so a device whose replies do not reach TasmoFleet leaves at most one write unknown per 10 minutes
  while HTTP works; its next commands and switches go over HTTP for a while. While HTTP is known to fail nothing
  marks it (MQTT is then the only way), so each write over MQTT can end unknown.
- **Low.** A light write over MQTT (T21) is confirmed by a STATUS11, and a STATUS11 carries nothing that ties it to the
  `Status 11` that asked for it, as for any `Status 11` read TasmoFleet sends. A single write takes it only after its own
  response, so a STATUS11 asked before the write ran (ours overtaking the write on the other topic, `cmnd/<topic>/Status`
  after `cmnd/<topic>/Dimmer`, or another client's) is skipped and the write ends unknown, unless another RESULT (a
  button press, another client's command) reached TasmoFleet ahead of that STATUS11: any non-retained RESULT counts as the
  write's response (`writeResponse`), so the early STATUS11 then confirms the write with the state from before it. That
  needs two foreign messages in a row, in a window of milliseconds. What remains is another
  client's `Status 11` answered between the write's response and ours: it shows the state after the write, and our own
  STATUS11 is then left in flight and can answer the next command on the topic that takes one. For a `Backlog` the
  window is its whole run: another client's `Status 11` at any time while the `Backlog` drains answers its appended
  `Status 11`, and the `Backlog` is reported done with a state from before its later parts, which still run on the device.
- **Low.** A discovery config that names a stored device's topic with another MAC (T19, #876) makes the broker reader ask that
  topic once through the router's own check: anyone who can publish on `tasmota/discovery/#` can cause at most one `Status 5`
  window per device per 10 minutes and at most 2 per 30 s pass (the rest wait for later passes). A check takes 1.5 s, up
  to 8 s for a device whose last will says Online but which does not answer, and the reader serves nothing else meanwhile,
  so that is the most the reader is held per pass. Such a publisher cannot mark a device without answering the check on the
  device's own topic. The broker ACL ([guide](../mqtt-broker-acl.md)) is the protection against that.
- **Low.** A taken topic (T19) is found by the checks that hear every `Status 5` reply within 1.5 s (since #804 and
  #878 every check that vouches for a read over MQTT); a second device whose reply comes later than that is not heard,
  and the mark, once set, ends only on such a check that finds the device alone (T19). A failure counts as a reply only
  after the first one: when the first reply in the window is a failure (`{"Command":"Unknown"}`, a second board in
  minimal firmware answering faster than the stored device), the check ends with that error before its window, learns
  nothing and marks nothing, so such a board is not found while it keeps answering first; the reads stay refused or go
  to the address, but writes to the topic still reach it. The reads after a check (the data
  refresh's, the broker read's) each hear one reply, so a second device that joins the topic between the check and a
  read could answer it first; the next check finds and marks it. Every such check waits the 1.5 s window after the first
  reply: the Settings tab and the policy poller per read of a device read over MQTT, and the broker reader, which is
  serial, per data refresh, broker read and network facts read of such a device. While HTTP is known to fail, the reads of a marked device still go to the topic (MQTT is the only way left): the
  broker read, the data refresh and Refresh identity over MQTT read there only after the check that hears every reply
  found the device alone, which ends the mark; the Settings tab and the policy poller read there but their check after the
  reads refuses on the taken topic without asking it, so they show nothing
  read on it; a read typed in the console shows
  whichever device answers. Once the topic is free the mark ends at the next topic check, within 10 minutes (sooner when a
  person runs Refresh identity over MQTT); until then a device whose HTTP fails has no path for its writes, backups and
  restores. The topic check is skipped while a job holds the device and finds nothing while MQTT is not usable for the
  device; the mark stays then. The mark lives in memory; after a restart of TasmoFleet the next check sets it again.
- **Low.** The identity over MQTT (T20) is checked by one window that hears every `Status 5` reply; the reads after it
  (`Status 2`, `Status 4`, the facts) each hear one reply. A second device that joins the topic in the second or two
  between the check and those reads could answer one of them first, as for the facts since #851; the next check, at
  the latest the next identity refresh, finds and marks it. Every probe of a device read over MQTT waits the 1.5 s
  window.
- **Low.** The background reader of #87 (`mqttIdentity`: INFO1 and one `Status 2` over MQTT, without a MAC check)
  still fills version, image and hardware of a device no probe has identified yet (`identity_at` unset). It never sets
  `identity_at`, never writes flash or language, and the first probe (over MQTT after its check, or at the address)
  replaces what it wrote. A rule kept apart from T20 that is to be folded into the probe.
- **Low (#1005).** GroupTopic2 to GroupTopic4 changed outside TasmoFleet (the device's web UI or console, another MQTT
  client) are seen only at the device's next probe: INFO1, which every boot publishes, carries GroupTopic1 alone, and
  the stamp of GroupTopic2 to 4 stays that of their last read until a probe makes it stale. Every GroupTopic write
  restarts the device (`restart_flag = 2`, `CmndGroupTopic`), and a restart starts an identity refresh (the probe
  reads the bare `GroupTopic`) unless one ran in the last hour (`restartRefreshEvery`); otherwise the periodic
  identity read catches it. TasmoFleet's own changes are not in this gap: a `GroupTopic<n>` with a value that may have
  reached the device (console, bulk command, update job: `holdingCmd`, any part of a `Backlog`) and a restore upload
  that may have reached it (the dump carries them) mark GroupTopic2 to 4 unread at once (`store.ForgetGroupTopics`,
  the values are kept) until the reader has read them again (a restore reads them itself once the device is back,
  before its verifying backup); until then the device holds back the other devices' MQTT writes as above. One narrow
  race is left: the reader takes no device lock, so a read of an already unread list that is in flight while such a
  write runs can store the answer from before the write; the write restarts the device, and the restart refresh
  or the periodic identity read above reads the list again. A device whose firmware does not answer all four keys `GroupTopic1` to `GroupTopic4`
  (every pinned release from 12.5.0 to 16.0.0 does) stays unread and holds back MQTT writes, which fails closed.
- **Low (#812).** A device with an unread GroupTopic holds back the writes and transfers over MQTT of every other
  device only while it may be on our broker. Its GroupTopic is free text (`CmndGroupTopic` passes it through
  `MakeValidMqtt`, which replaces only `+`, `#` and spaces; Tasmota 16.0.0 `xdrv_02_9_mqtt.ino` 181-200), so it could equal any device's topic, and no device is exempted by comparing topics. It is
  left out when it is provably not on our broker: its last `Status 6` put it on another broker or on none; nothing
  TasmoFleet knows ties that broker to ours (no device stored as ours names the same host and port, and the broker
  matcher with its aliases, #597, does not accept it: `Status 6` is classified without aliases, so a device configured
  with the broker host's LAN address is stored as "other" while it is on our broker); and nothing from its topic was
  ever heard on ours (no last will, which Tasmota publishes retained on every connect, and no other message, under any
  device with that topic), where its will would be heard (its FullTopic is `MQTT_FULLTOPIC`, its topic one level) and
  once the bus has been subscribed for 30 s (`willReplayGrace`, from `mqttbus.ConnectedSincer`), so the broker has
  replayed the retained wills after a start, a reconnect or a broker change; before that, and while the bus is down,
  every such device counts. Silence counts only while it can mean something on the current connection (#972, the bus's
  will ledger, `mqttbus.WillLedger`, reset on every connect): the bus has heard at least one will since it
  subscribed (Online, Offline or cleared; a live telemetry or reply message does not count, it proves only that stat
  or tele is readable, not the wills; a broker ACL that lets TasmoFleet publish but not
  read hears none, and every device would look "never heard"), and no device is up under a topic no stored device has
  (a device that moved to our broker with a new topic is heard only there, nothing ties it to its stored record, and it
  could be any of the exempt ones). A topic is up after a will that is not Offline, or after a live (not retained)
  telemetry or reply message under it (the rule the health tracker uses for "heard", so an unknown device whose
  retained will was deleted before this connection subscribed, or a broker that keeps no retained messages, is seen at
  its next telemetry, at most its `TelePeriod`); only an Offline will takes it down. A cleared will (empty payload,
  someone deleted the retained message) keeps the topic's last state, as the health tracker keeps a stored device
  heard: the device is still connected and its will still registered with the broker. The trade-off, fail closed:
  clearing the stale retained Online of an unknown device that is gone ends its hold only from the next connection
  on. A retained telemetry or reply message does not bring a topic up (it may be a gone device's), and neither does a
  discovery message (its topic is a MAC). An unknown topic whose latest will is Offline does not count, a deviation
  from "anything heard" in #972: Tasmota leaves a retained Offline on its old topic at every topic change (#119), so
  counting it would end the exemption for good in most fleets, and an Offline device cannot receive our commands
  (never retained). The ledger keeps up to 4096 topics; past that it says it is incomplete and no device is exempt
  until the next connection.
  What this costs, on purpose (fail closed): while any Tasmota that is not in the inventory is Online on our broker (a
  partly adopted fleet, another tool's devices), no device is exempt, and the writes, transfers and update commands of
  the devices held back go over HTTP as before #812; that is not a regression. A device that connects to our broker
  with its stored topic is heard at once, and the next
  call counts it again (the facts are computed for every routed call). What is left: a device outside the inventory
  whose will goes to a topic shape the bus does not decode (another FullTopic or `Prefix3`), which the ledger does not
  see; a broker ACL that denies reading only some devices' topics while others are heard (the ledger proves only that
  reads are not denied as a whole); a device in the inventory that is on our broker under a broker host
  nothing ties to ours (no alias evidence, no device stored as ours with it) and whose will goes to a topic the bus does
  not decode: a FullTopic or telemetry prefix (`Prefix3`) other than the stored ones, which a device added by its
  address never had read (its FullTopic is taken as the default, `Prefix3` is not stored); a bridge that carries our
  command topics to its broker in one direction only. Three narrower cases of "not heard": a device just added or
  given a new topic is not heard until the health tracker has picked it up (its next tick); the health tracker keeps
  the last wills of at most 1024 topics, so on a larger broker a device added or given a new topic later
  can miss its replayed will until its next telemetry (the probe at add reads its GroupTopic, which ends the case);
  and a retained will someone cleared leaves the device unheard until its next telemetry (at most its TelePeriod).
  Being wrong in any of these needs the device on our broker, HTTP not reaching it (else the GroupTopic reader reads
  it over HTTP) and its GroupTopic equal to the written device's topic.
- **Low.** The reply scrub masks values by their JSON key name (password, token, SSId, ...) and, since #605, the
  exact keys `KeyL`, `KeyH` (`ZbConfig`) and `MIKeys` (`MI32Key`/`MI32Keys`); a key under any other name a device
  answers with reaches the admin who sent the command, over HTTP as over MQTT, as before #605. cmdpolicy, its
  policy rules, the reply scrub and the backup diff each decide by their own rule what is secret; #809 makes it
  one rule.
- **Medium, by design.** A write over MQTT is delivered by the broker to every client subscribed to the device's
  topics, and on a usual Tasmota it is plain text on the device's leg (see "What changes compared with HTTP"):
  a password, a key or a login set over MQTT can be read there. Over HTTP the same command crosses the network in
  plain text too, with the device's web password beside it. Restrict the device topics with a broker ACL ([guide](../mqtt-broker-acl.md)).
- **Medium, by design (#607).** A backup or restore over MQTT puts the whole settings dump (Wi-Fi, web and MQTT
  passwords, tokens, keys) and the device's MQTT password on the broker, which delivers them to every client
  subscribed to the device's topics; on a usual Tasmota the device's leg is plain text. Over HTTP the dump is plain
  text on the network too. This happens on every scheduled backup. Restrict the device topics with a broker ACL
  (see "Backups and restores over MQTT").
- **Medium, by design (#924).** A backup over MQTT of a firmware built with `USE_UFILESYS_MQTT` puts every file of
  the device's flash on the broker (Berry scripts with their tokens, the TLS private key `/tlskey`), and the device's
  MQTT password once per file. Same class as the dump: restrict the device topics with a broker ACL (see "Backups and
  restores over MQTT"). It is no reason for HTTP, which carries the same files in plain text with the web password.
- **Low.** The files of a backup over MQTT on a stock firmware or a device with an SD card are read over HTTP from the device's address after a `Status 5` that
  reports its MAC; the check and the reads are separate requests, so a host that takes the address over between them
  (a DHCP lease handed on within seconds) could hand over its files. A restore checks the MAC over HTTP right before
  the files, as an HTTP restore does (R30); the settings of a restore over MQTT go by topic and are bound by R27. The
  MAC question goes without the stored web password; a host at the address that demands a password (another Tasmota
  with one) gets the stored credentials with the second question, as for an HTTP restore (R13).
- **Low.** A restore over MQTT that changes the MQTT connection proves HTTP at the start and right before the upload
  with `Status 5` over HTTP (the device's MAC); HTTP can still be lost by the change itself (an address that changes
  with the reconnect), as for a write (T10). The wait for the restart asks HTTP only after such a restore, and only
  when the old topic is silent; the check backup then goes over HTTP.
- **Low.** "HTTP works" means HTTP answered the router's `Status 11` right before a change of the MQTT
  connection; an answer on record does not count, unknown is not usable. Without that answer such a change needs
  the console's confirmation. HTTP that answers can still lose the device after the change for reasons TasmoFleet
  does not see (the address changes with the reconnect), and the answer does not prove by MAC that HTTP reaches the
  same device (the health poll's does not either). A person who confirms the change on a device HTTP does not reach
  takes the risk the confirmation names. Each such change costs one `Status 11` (up to the HTTP timeout, 10 s, on a
  silent device).
- **Low.** After such a change the device's next commands go over HTTP for 10 minutes (T10), also when it rejoined
  the broker at once: HTTP then carries them as before #605. Only an answer on a path that still uses MQTT (a pinned
  job, HTTP failing) ends the mark earlier. A device that cannot rejoin is marked only by the router of this
  TasmoFleet and only for those 10 minutes; after that, with its last will still `Online`, the next read, write or
  power switch over MQTT goes unanswered and marks it again (T11): one unknown outcome per 10 minutes at most. The
  marks live in memory: a restart of TasmoFleet forgets them.
- **Low.** A device with `SetOption10 1` publishes its last will `Offline` on the old topic before it answers a
  changed `Topic` or `FullTopic` (Tasmota `xdrv_02_9_mqtt.ino` 1566-1567 and 1675-1676; with the default
  `SetOption10 0` the will is cleared instead). The channel takes `Offline` as the end of the wait, so such a change
  over MQTT is reported as an unknown outcome although it ran; nothing resends it (T3).
- **Low (#608).** An update pins its path when it is made; a scheduled one may start hours later. Its pinned
  `OtaUrl` and `Upgrade` are checked against the strict rule right before each publish (`Router.pinnedMQTT`), and its
  reads are refused on a topic marked as taken (T19), so a topic that became shared since then sends nothing and the
  job fails, with no identity from it stored; it never moves to HTTP, even while HTTP
  works. The same holds when the device does not come back on the broker within the reboot window: the job fails
  with "restart the device and retry the update" although HTTP may answer (D5, #810). A retry chooses its path
  again. The off-broker exemption of the strict rule (#812, above) now also decides whether `OtaUrl` and `Upgrade 1`
  may go to a topic: a device wrongly exempted whose GroupTopic equals this device's topic would get the same
  `OtaUrl` and `Upgrade 1` and flash an image that Guard checked only for this device: over MQTT the topic is the update's identity, bound
  by the strict rule and the T19 marks, and no MAC is checked. It needs every condition of
  the #812 risk above; a restore over MQTT (`FileUpload` Type 2) already depends on the same rule.
- **Low.** A queued bulk command job and a retry keep the route their preview named (#826), not its sentence: the
  router checks the route when the job sends, not the broker URL. When an admin changes the URL from `mqtts://` to a
  plain one between the run and the send, the job crosses the broker under the confirmation given for the TLS
  sentence; TasmoFleet's leg was the only difference. The console and the bulk run check the sentence again.
- **Low.** The bulk preview's button still counts the devices a command goes nowhere to (#826: MQTT does not carry
  it and their HTTP fails); their row says "Not sent" and the run leaves them out.
