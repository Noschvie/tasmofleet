# Policy rule templates checked against the Tasmota 16 source

The New rule page offers templates (`internal/web/policytemplates.go`). A rule is only worth
having if tasmofleet can read the setting without side effects, compare what the device answers
with what the rule says, and set it with Make compliant. This note records that check, one row
per template, from the Tasmota source. `TestTemplatesReadableAndComparable` keeps the result true.

## Source

- Repository `arendst/Tasmota`, branch `development`, commit `c1c6a82c68415ed2a856456c9d1a532d5b28c0a8`
  (2026-10-29), `TASMOTA_VERSION = 0x10000001` (16.0.0.1, `tasmota/include/tasmota_version.h`).
  This is the 16.0.0 line plus one commit; no function cited below was changed between the
  v16.0.0 tag and this commit as far as the checkout shows, but the tag itself was not diffed.
- Paths are relative to `tasmota/` in that tree. Line numbers are those of the commit.
- Default build (`my_user_config.h`). A build without a feature answers `{"Command":"Unknown"}`,
  which the settings reader treats as "not judged", never as a deviation. That matters for
  Latitude and Longitude (`USE_SUNRISE`, default on, `my_user_config.h:563`).
- Nothing was run on a real device. Reply shapes come from the response macros and the Cmnd
  functions; the simulator now answers exactly those shapes.

## What the check found

1. **Sleep** (already fixed in 0.18.0): the reply is the nested object above. `replyScalar` /
   `sleepConfigured` read the configured value, the simulator answers the real shape, and the
   Sleep template is covered by `TestTemplatesReadableAndComparable`. SerialLog and SysLog use the
   same macro (1382, `CmndSyslog`).
2. **Latitude and Longitude cannot be compared as answered.** The device stores
   `(int)(float32 * 1000000)` and answers `(float32)n / 1000000` with six decimals. Typing
   `40.12` gives `40.119999`, so a rule on `40.12` or `40.120000` never matches, and Make compliant
   would resend it on every check. A float32 has 24 bits of mantissa: the error reaches about
   2e-5 degrees near 180. `settings.replyScalar` therefore rounds these two replies to four
   decimals (11 m). A rule's expected value gets the same form: `settings.CanonicalWant` turns
   whatever the admin typed (`52.52`, `52.520008`) into `52.5200` when `policy.ParseRules` reads
   the rule, and refuses what is not a number in range (`52,52`, `91`). The stored rule keeps what
   was typed; the comparison and the command Make compliant sends use the four-decimal form, so a
   rule converges instead of being resent forever. Set and read back agree for every four-decimal
   value in the simulator (`TestCoordinateRulesSurviveTheFloat32RoundTrip`,
   `TestCoordinateWantsConvergeWhateverTheAdminTyped`).
3. **TelePeriod is not a pure query** (see the table); it is read from Status 3. The template
   works as before.
4. **The simulator accepted `LedState 8`.** `MAX_LED_OPTION` is 8 and the check is `< 8`.
   Fixed to 0..7. It also had no Latitude, Longitude or PowerRetain; all three now answer as
   above.
5. **OtaUrl**: setting the URL never starts an update, and `fwselect.Guard` runs before the
   `OtaUrl`/`Upgrade` pair of an update, which a policy rule does not send. A rule can still point
   a fleet at a wrong file for the next update; the firmware check still runs then. The ESP32
   template is blank for the same reason (variants differ).

## Dropped

None. Every template in the plan is kept.
