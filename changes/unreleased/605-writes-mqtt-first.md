section: Changed
---

Changes go over MQTT first, like reads since 0.30.0: console and settings writes, Restart, bulk commands and the switches of a device that is online on TasmoFleet's broker with its own topic (its group topic read, and every other device's) are sent over MQTT, and over HTTP only when MQTT cannot carry them or nothing could be published. That holds whatever a change carries: a password, a Wi-Fi name, a login inside a command, a GPIO template and a change of the device's MQTT connection (topic, broker, login) go over MQTT first too. HTTP to a Tasmota is plain text as well, but over MQTT the broker hands a command and its reply to every client subscribed to the device's topics: give the broker an ACL that lets only TasmoFleet and the device read them. The audit log, the console history and the replies keep hiding secrets as before. While HTTP reaches the device (it answers a quick Status 11 TasmoFleet asks right before), a change of its MQTT connection (MqttTLS and MqttTLSFingerprint included, which Tasmota runs as SetOption103 and SetOption132) is sent without a question, and the device's next commands then go over HTTP for about ten minutes, whichever way the change went, so a device that does not come back to the broker after the change, a mistyped MQTT password for instance, is still reached and can be corrected; otherwise the console asks first, a bulk command or Make compliant leaves that device out and the settings page reports it as not sent. The bulk preview and Make compliant's plan refuse such a change up front only for devices whose HTTP is known to fail. Opening a device's console now checks its HTTP, as its page does. Commands that run other commands (Json, If, WebSend, a rule text, DevGroupSend, LoRaCommand, a GPIO template with a CMND part and the like) and Backlog2/Backlog3 still go over HTTP: MQTT does not carry them (If, DevGroupSend, LoRaCommand and a template with CMND are now refused over MQTT like the others). A change MQTT sent and the device did not confirm is reported as an unknown outcome and never sent again; the device's next commands then go over HTTP for a while. A device reply no longer shows the Zigbee network key (KeyL, KeyH) or the BLE bind keys (MIKeys). The audit names the transport, and the device page's "How TasmoFleet reaches this device" card says which way changes go and why; the console's title names the transports ("MQTT + HTTP", "MQTT" or "HTTP") instead of always "HTTP". The console and bulk commands now ask for a confirmation before they set RgxPassword or RgxSSId (the range extender's Wi-Fi password and name) or WiFiTest (a Wi-Fi name and password to try), as for the other passwords and Wi-Fi names, and before MI32Key, MI32Keys or ZbConfig with a value, naming what a wrong key or a changed Zigbee network does (#605)
