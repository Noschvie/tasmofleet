# CLAUDE.md: rules for AI agents (and humans) working on tasmofleet

Read this file first, then the parts of the spec you need
(`docs/spec/2026-10-18-tasmofleet-design.md`). Human contributors: see also
[CONTRIBUTING.md](CONTRIBUTING.md).

## Ground rules

- **English only** in everything committed: code, comments, docs, commit messages, test names.
- **Test first.** Write the failing test, then the code. Tests say _why_ the behaviour
  matters (a comment or the test name), not just what it does. A test that cannot fail
  when the business rule changes is wrong.
- **No network in unit tests.** Only loopback listeners the test itself starts
  (`httptest`, the simulator, the embedded MQTT broker, the mock OIDC provider). Nothing
  reaches the internet, a real broker or a real device. Integration tests (build tag
  `integration`) follow the same rule.
- **Stay inside your change's scope.** You may read everything, but change only the
  packages your change is about. If a contract (interface or type
  in `internal/model` or another package's exported API) has to change, stop and
  report it instead of editing it. Contract changes go through the spec.
- **Minimal dependencies.** The allowed modules are listed in the spec ("Dependencies").
  Adding one needs a written justification in the spec in the same change.
- **Fail loud.** Never report "done" or "tests pass" if anything was skipped. No
  `t.Skip` without an issue reference. No ignored errors (`_ =` only with a comment
  saying why).
- **Match conventions.** gofmt, `log/slog` for logging, `errors.Is/As`, context on every
  I/O call, table tests, `t.TempDir()` for files.

## No backward-compatibility shims

tasmofleet has no stable external API before 1.0 (maintainer's rule).
Don't add or keep compatibility layers: no redirects for moved routes, no deprecated
config/env aliases, no old CLI command names, no API compat layers. Breaking changes are
fine. Record each one in `CHANGELOG.md` (section "Unreleased", then the release).
**The only exception is user data:** migrations stay append-only, and the live database
must upgrade cleanly.

## Product principles (details in spec §1.1a)

- **Minimal mandatory configuration**: environment = bootstrap only. Every other setting
  (SSO included) is live in the UI and stored in the database; env values lock their
  field. New settings get a UI/DB setting, not a new environment variable.
- **Proportionate security (home-lab tool)**: keep the basics (CSRF, authz, no secrets in
  logs/HTML, chip-family guard, secrets only to their bound target). Step-up only for
  local account management and auth/SSO changes (not for restore, 2026-10-20). Reviews: fix High/Medium,
  document Low/Info as residual risk, no review loops.

## Package boundaries (enforced by depguard in `.golangci.yml`)

- `internal/model` imports only the standard library.
- `internal/fwselect`, `internal/cmdpolicy` and `internal/ota/machine*.go` are pure: no `net`, `os`, `database/sql`.
  They take data and return decisions. These are the safety-critical parts; they are in
  the weekly mutation run and their changed lines are gated by diff coverage in every PR.
- `internal/tasmotacmd` (and its `extract`) is pure too (same depguard rule) but not under mutation testing
  or in `SAFETY`.
- Only `internal/store` imports `database/sql` / `modernc.org/sqlite`.
- Production code never imports `internal/simulator`, `internal/testutil/...` or the
  embedded MQTT broker.
- `github.com/a-h/templ` is imported only by `internal/web` and `internal/web/ui`. `templ.Raw`,
  script and css components, `style` attributes and inline handlers are forbidden (CSP;
  `forbidigo`, a source test in `internal/web/ui`).
- Consumers depend on interfaces (`store.DeviceStore`, `tasmota.Client`, `ota.DeviceAPI`, ...),
  never on concrete types from another package. Fakes live in the consumer's `_test.go`.
- Device network access goes only through `tasmota.Client` with a `tasmota.Target`
  built from an inventory device. Firmware downloads go only through `firmware`
  sources. Nothing else makes outbound HTTP requests (the notification webhook sender in `notify`, OIDC discovery and the SSO connection test in
  `auth` are the configured exceptions, and so is the `healthcheck` client in `cmd/tasmofleet`,
  which only calls the service's own loopback address).

## Generated code: templ

`*.templ` files are the source; the `*_templ.go` next to them are generated and committed (so
`go build` and the Dockerfile need no generator). Never edit a `*_templ.go`. After changing a
`.templ`, run `make templ` and commit both. `make templ-check` (part of `make check` and the CI
lint job) regenerates and fails when that changed a file. The generator is pinned in
`tools/go.mod` and its version must equal the `github.com/a-h/templ` version in `go.mod`
(bump both together). Every page renders inside `ui.Shell`; there are no html/template pages.

## Safety rules that must never regress

1. `fwselect.Guard` runs immediately before every `OtaUrl` and `Upgrade`. It refuses on
   unknown hardware, chip-family mismatch (device vs artifact header vs file name), safeboot
   images, and variant changes without explicit user choice. Never bypass it, never "guess".
   Guard covers what TasmoFleet sends on its own (update jobs, restore, Make compliant). An
   `Upgrade`/`OtaUrl` typed in the console or sent as a bulk command is the person's
   responsibility after the confirmation (`cmdpolicy.whyFirmware`); the one hard rule there is
   that it is refused while a TasmoFleet update job holds the device (`cmdpolicy.StartsFirmware`).
2. `Status 0` is never sent by automated code (heap bursts corrupt ESP8266 replies). Use
   individual `Status N` queries, one at a time per device.
3. `Upgrade 1` is never retried blindly. After a lost response the engine probes first.
4. Device credentials never reach the browser, logs, errors or audit details.
5. Local accounts are managed by the CLI or by admins in the UI (`/users`) with step-up: the
   current password for local admins, the IdP re-authentication for OIDC admins. Header
   principals have no step-up and only view. Operators can never create accounts or raise
   roles. Listing needs no step-up, every change does.
6. Forwarded headers are trusted only from `TRUSTED_PROXIES` (checked on `RemoteAddr`).

## The Tasmota simulator

`internal/simulator` replays real captures from `testdata/fixtures/devices/` and models
the OTA state machine documented in `docs/research/tasmota-minimal-and-ota.md`
(pending, downloading, reboot gap, minimal firmware with its 5 commands, settings not
persisted in minimal). Use it for every test that would otherwise need a device:

```go
fleet, _ := simulator.NewFleet(simulator.FleetOptions{FixturesDir: "../../testdata/fixtures"})
dev, _ := fleet.Add(ctx, simulator.DeviceSpec{Name: "plug", Profile: simulator.ProfileESP8266_1M, Version: "15.6.0"})
// dev.Addr() is a loopback host:port; dev.Commands() records what was sent
```

Fault injection (`simulator.Fault`) covers timeouts, dropped connections, unknown
commands, auth failures, failed downloads, long reboots and wrong-family firmware. Add a
fixture or a fault instead of mocking HTTP by hand.

## Running the gates

| Gate                                                                      | Command                                                                       |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| FAST tier, everything but e2e (run before every commit)                   | `make check`                                                                  |
| inner loop between two edits (not a gate)                                 | `make quick`                                                                  |
| FAST tier, the `@core` e2e tests                                          | `make e2e-core`                                                               |
| FAST tier, a safety package changed (race + diff coverage + revert check) | `make safety BASE=origin/main`                                                |
| every changed SAFETY line is executed by a test                           | `make diff-cover BASE=origin/main`                                            |
| the tests you changed fail without your production change                 | `make revert-check BASE=origin/main`                                          |
| FULL tier, everything CI runs nightly and weekly                          | `make ci TESTFLAGS=-count=1`                                                  |
| format                                                                    | `make fmt` / `make fmt-check`                                                 |
| go vet                                                                    | `make vet`                                                                    |
| staticcheck (also inside `make lint`)                                     | `make staticcheck`                                                            |
| golangci-lint (incl. depguard boundaries)                                 | `make lint`                                                                   |
| unit tests                                                                | `make test`                                                                   |
| integration tests                                                         | `make integration`                                                            |
| race detector                                                             | `make race`                                                                   |
| mutation tests (MUTATION in the Makefile), optional                       | `make mutation` / `make mutation-changed BASE=<ref>`                          |
| e2e (Playwright), all but quarantined                                     | `make e2e-deps` once, `npx playwright install chromium` once, then `make e2e` |
| quarantined tests (nightly only)                                          | `make test-quarantine` / `make e2e-quarantine`                                |
| vulnerabilities                                                           | `make vuln`                                                                   |

Tools are pinned in `tools/go.mod` and run via `go tool -modfile=tools/go.mod <tool>`.
Run a single package's tests with `go test ./internal/fwselect/ -run TestGuard -v`.
`make quick` runs fmt-check, vet, golangci-lint and the tests (the integration tests only when their package is affected) on the packages
changed since `origin/main`, uncommitted and untracked files included, and on every package that imports them; a changed file outside every package
(docs, assets, deploy, tools, a `testdata/`) makes it run everything, because tests read such files. It skips templ-check, scripts-test,
shards-check, migration-append-only, vuln and build: `make check` stays the gate before every commit.
Parallelism follows the machine: `JOBS` defaults to `nproc` (`GOFLAGS=-p=$(JOBS)`),
mutation workers to `nproc/2`, Playwright workers to `E2E_WORKERS` (default 6). Locally the Makefile runs tools under `nice -n 15`; CI sets `NICE=` (empty). Override
with e.g. `make check JOBS=4`. `make test` and `make integration` use the go test cache
(unchanged packages report `(cached)`); `TESTFLAGS=-count=1` forces a fresh run. `make integration` runs only
the packages that have `//go:build integration` test files (found at run time, anywhere in the module); only `_test.go` files may carry the tag.
`make check` runs `shards-check` only after a change to the Makefile, `tools/`, a `go.mod` or the package list (CI runs it every time).
**Before you push** (builders): `make check`; when you changed a `SAFETY` package, also `make safety BASE=origin/main`; for every fix
`make revert-check BASE=origin/main` (it takes seconds and is what the PR's `revert check` job runs).
`make diff-cover` runs the tests of the changed SAFETY packages once with a coverprofile (integration-tagged tests included) and fails
for every line you added or changed in a non-test Go file of a SAFETY package that no test of that package executes; comments,
declarations and braces carry no code and are not checked. `make revert-check` copies the tree to a scratch directory, puts the production
`.go` files you changed back to the merge base (files you added are removed, deleted ones restored), keeps the tests, and runs the tests you added or
changed (the whole package when you changed a helper, a table or an import). At least one of them must fail, or the package must stop building
(a feature whose tests use new API); a selected test that never ran or skipped (no decoder, a quarantine) is an error. The output lists every test that fails and every one that passes
either way. A PR that changes production code without any test is not stopped by it (diff coverage covers the SAFETY packages). **Opt-out** for a pure
refactor or a feature where nothing should fail: a line `revert-check: skip - <reason>` in the PR body, or the label `no-revert-check`;
the job reads both from the API when it runs, so after adding it re-run the job. The gate prints "SKIPPED" and the reason; locally
`REVERT_CHECK_SKIP="<reason>"`. Both gates diff against the merge base with `BASE` (default `origin/main`), uncommitted and untracked files included.
Mutation testing is not part of any PR (#555, the maintainer finds it makes PRs wait and rarely catches anything):
`make mutation-changed BASE=<ref>` mutates only the lines this branch changed since the merge base in the MUTATION packages it touched, and
`make mutation` every package whole (the weekly full run, a report until the keep-or-drop decision at the end of November 2026).
Any changed test or data file of a package (or an untracked source file in it) mutates that package whole, so weakened tests
cannot hide behind a small code change. On the changed lines a mutant no test reaches counts as lived. Fewer than 10 decided mutants
on the changed lines (`MUTATION_DIFF_MIN`) are too few for a percentage: such a diff passes with at most one lived mutant but needs a
kill, and one without any decided mutant (a comment, a declaration) passes and says so. Details and the
gremlins `--diff` traps they work around: header of `tools/mutation-gate.sh`. A sharded run leaves `mutation-report.json` and a job
summary (lived, timed-out and not-covered mutants per package) next to the counts (`tools/mutation-report.sh`).
gremlins builds every mutant, and each build is garbage afterwards (+261 MB per `internal/cmdpolicy` run), so the gate runs it with a throwaway `GOCACHE`
next to your Go cache that it removes when it ends (#546): neither your Go cache nor the one CI saves ever holds a mutant build (`MUTATION_GOCACHE_SEED` warms it, header of `tools/mutation-gate.sh`).

### Test tiers in CI (`.github/workflows/`)

One workflow per trigger. The file a run comes from is its tier; only `pr.yml` looks at the diff (docs-only,
SAFETY package, catalogue, image paths). Every gate runs through the Makefile.

| File                                         | Trigger                                    | Runs                                                                                                                                                                   |
| -------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pr.yml`                                     | `pull_request`                             | FAST: `changes`, `checks` (with diff coverage on SAFETY PRs and the revert check), link check, migration and release section guards, image build check, **`required`** |
| `main.yml`                                   | push to `main`                             | lint, unit and integration tests, build (no e2e; saves the Go caches), `:edge` image and HA app image, then `ghcr-cleanup`                                             |
| `release.yml`                                | tag `v*`                                   | `guards` (incl. green `required` + `main.yml` of the SHA), then `publish` (image), `release`, `pages`; no checks. Dispatch = dry run                                   |
| `nightly.yml`                                | cron 22:37 UTC, `workflow_dispatch`        | FULL: `checks` (e2e all, `-count=1`, catalogue), `race`, `quarantine`, `ha-app`, `ghcr-cleanup`                                                                        |
| `weekly.yml`                                 | cron Sunday 21:13 UTC, `workflow_dispatch` | the full `mutation` run (all MUTATION packages) and its gate, the only place mutation runs                                                                             |
| `_checks.yml`, `_mutation.yml`, `_image.yml` | `workflow_call` only                       | the shared jobs; the caller's `with:` says which (inputs `e2e`, `e2e_shards`, `testflags`, `safety_race`, `diff_cover`, `revert_check`, `catalogue`, `scope`, `mode`)  |
| `_failure-issue.yml`                         | `workflow_call` only                       | the issue for a failed scheduled run: failed jobs, failed tests, commits since the last green run                                                                      |
| `ghcr-cleanup.yml`, `pages.yml`              | `workflow_call`, `workflow_dispatch`       | registry pruning (manual run: dry-run preview), the demo site                                                                                                          |

- **FAST** (`pr.yml`; `required` must be green to merge, target ≤ 5 min):
  lint, unit and integration tests, build, and the `@core` e2e tests in two shards plus the MQTT specs in a job of their own.
  When a PR changes a package listed in `SAFETY` (Makefile: fwselect, ota, tasmota, secretbox, auth, httpx,
  policy, cmdpolicy, mqttcmd, transport, restore), the race tests of the changed ones and diff coverage (`make diff-cover`) run too, and are then
  required. Every PR that changes Go code also runs the revert check (`make revert-check`). There is no mutation testing in the PR path (#555);
  the weekly run shards it in four (`MUTATION_SHARD`, files dealt out by estimated cost, `tools/mutation-weights.txt`) and gates on their sum
  (`make mutation-sum`). CI restores the Go build/test cache (`.github/actions/go`, keyed on Go
  version and `go.sum`) and sets file mtimes from git (`tools/git-mtimes.sh`), so unchanged packages
  are not retested: their results come from the cache that `main.yml` saves. Only runs on `main` save caches (`main.yml`,
  `nightly.yml`, `weekly.yml`; the Go caches, the npm and Tasmota-source caches alike): a cache saved by a PR or a tag run
  can be restored by nothing else and only evicts main's (#476).
- **Push to `main`** (`main.yml`): lint, unit and integration tests and the build, but no e2e: `main` moves only by a
  fast-forward push of a PR head that was green, so the e2e shards would repeat the PR (#478). The tests run, cacheable, so
  that main's go test cache holds their results for the PRs and tags (the nightly runs `-count=1` and stores none); the
  e2e caches are refreshed by the nightly. The `:edge` image and the HA app image follow.
- **RELEASE** (`release.yml`, tags `vX.Y.Z`): no tests of its own (#554). `main` moves only by a fast-forward push of a
  green PR head, so the tagged commit has already passed the FAST tier on its PR (`required`) and lint, unit and integration
  tests and the build on `main` (`main.yml`); running them again on identical code only delayed the image. Job `guards` fails at once, with the reason, when the
  tag is not on `main`, has no `CHANGELOG.md` section, is a patch tag that changes a migration, edits a migration of the previous tag,
  or when its commit lacks a successful `required` check run of `pr.yml` or a successful `main.yml` run (`tools/release-green.sh`;
  only `ghcr-cleanup` may fail there). Only the head of a push to `main` gets a `main.yml` run, and a push that changes only
  paths `main.yml` ignores gets none: tag the head of the push that carried the release commit, only after `main.yml` has
  finished on it. The race tests of every `SAFETY` package run in the nightly FULL on the same
  `main`. Then the image is published (job `publish` calling `_image.yml` with `mode: release`, the only way to push a tag
  image), then the GitHub release is made, then the demo site is deployed, each only after the one before succeeded.
  `workflow_dispatch` with a `sha` is a dry run of the green-commit check alone: it never publishes, releases or deploys.
- **FULL** (`nightly.yml`: cron on `main`, manual dispatch): additionally every e2e test in three shards plus the MQTT job, every
  unit test with the race detector (two shards: the slowest packages listed in `tools/race.sh`, all others; `make shards-check` fails when a package is in no shard), the command catalogue check, uncached test runs, and the Home Assistant app in a real Supervisor (`tools/ha-app-devcontainer-test.sh`). It blocks no release; when it fails on the schedule, the job `nightly-failure-issue` opens an issue "Nightly FULL failed on main (date)" (labels `ci`, `flaky`) with the failed jobs, the tests their logs name and the commits on `main` since the last green night, or comments on the one that is still open. GitHub starts the scheduled run 5 to 8 hours after its cron time, so the cron is set to land in the early morning. A manual run never opens an issue and only previews the registry cleanup. Layout and visual regressions and race outside the safety packages are caught here, so the nightly FULL is the place to look for them; a
  failure is fixed through an issue, not by holding a release.
- **WEEKLY** (`weekly.yml`: cron on `main`, Sunday night, manual dispatch): the full mutation run of every MUTATION package with its gate (`make mutation`
  in four shards, `_mutation.yml` with scope all). The nightly does not run it (#480), and no PR waits for it (#555), so this is where a surviving mutant shows up, once a week. It blocks nothing; when it fails on the schedule, the job `weekly-failure-issue` opens an
  issue "Weekly mutation run failed on main (date)" (label `ci`) or comments on the open one. The run also saves the mutation Go cache.
- **Which e2e tests are `@core`**: smoke, sign-in and authorization (header, local, OIDC, standalone,
  operators refused), first-run setup, base path, the device list, the OTA update flow (batch, push upload),
  the chip-family and OTA-exclusion refusals in the UI, device writes (console, settings, restore, make
  compliant). Tag with `test("title", { tag: "@core" }, ...)`. Layout, visual and component checks stay in
  FULL. Add a test to core when it guards a safety rule or the main path; keep the core run short.
- **Quarantine**: a test that fails without a code cause gets a GitHub issue (label `flaky`, failure evidence)
  and is quarantined: Playwright tag `@quarantine`, or `quarantine.Test(t, "<issue URL>")` from
  `internal/testutil/quarantine` for Go tests. Quarantined tests run only in the `quarantine` job of `nightly.yml`,
  with retries, and never block a PR or a release. Fix or delete each one within about two weeks; the fixing
  change removes the tag and closes the issue.

Docs-only PRs skip the checks; the link check (`tools/check-doc-links.py`), the migration guard (`make migration-append-only`)
and the release section guard (`make release-pr-check`) run on every PR and gate the merge. The list of docs
that are safe to ignore (and the ones a test reads, which are not) is in the header of `.github/workflows/pr.yml`.
Third-party actions are pinned to a full commit SHA with the version in a comment (`uses: owner/repo@<sha> # vX.Y.Z`);
Renovate keeps both current. Reusable workflows take their secrets by name (`secrets:`), never `secrets: inherit`.

## Commits

- Commits are signed; `main` requires signed commits (branch protection). **Never** disable signing
  (`--no-gpg-sign`, `-c commit.gpgsign=false`). If signing fails, stop and report it.
- Write the message with a quoted heredoc, never `-m "..."` with backticks or `$(...)`:

  ```sh
  git commit -F - <<'EOF'
  fwselect: refuse safeboot images in Guard

  Body in English: what and why.

  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  EOF
  ```

- Trailer `Co-Authored-By: Claude <Model> <noreply@anthropic.com>` on AI-authored commits, naming the
  model that actually wrote the change (e.g. `Claude Sonnet 5.5` for a Sonnet subagent).
  No session links or other URLs to chat sessions.
- Commit only your own files. `make check` must pass before each commit.
- Repository: `https://github.com/nofuturekid/tasmofleet` (HTTPS remotes).
- No secrets in the repository, not even in tests: use obviously fake values.
- **Migrations are append-only since tag v0.0.1.** Never edit a merged file in
  `internal/store/migrations/`; add `NNNN_name.sql`. `make migration-append-only` (part of `make check`, job
  `migrations` in `pr.yml`, tag job `guards`) fails when a file that exists at the newest `vX.Y.Z` tag in the branch's
  history is modified, renamed or deleted, uncommitted edits included. It needs the tags and fails without them (CI:
  `fetch-depth: 0`; locally `git fetch --tags`). (0001 was amended before the first tag;
  dev/test databases created before that must be recreated.)

## Releases

- **SemVer** from v0.1.0: new features or visible behaviour -> minor (`0.x.0`); bug fixes
  and small changes only -> patch (`0.x.y`). Breaking changes are allowed before 1.0 but
  must be listed in `CHANGELOG.md`.
- `CHANGELOG.md` has one section per version with the subsections Added, Changed, Fixed,
  Breaking and Security (empty ones omitted). Every merge adds its lines under
  "Unreleased". The release commit moves them into a new "## X.Y.Z "Name" (date)" section BEFORE
  the tag is set; the tag build fails when that section is missing
  (`make changelog-check TAG=vX.Y.Z`).
- **The release commit rides in the merge train** (#556): it is the last commit of the release's train (or of
  the single PR when there is no train), followed only by the release's demo-media refresh (`make demo-media`) when there
  is one, so one `required` run on its tip, one fast-forward and one `main.yml` run cover the release. A separate release
  PR only when the release has nothing else to merge. When a PR's tip adds a new
  `## X.Y.Z` section, its CI runs the tag's guards (`make release-pr-check BASE=origin/main`: `changelog-check` and
  `migration-guard`); run it locally before pushing a train. The demo-media refresh must be in that same push: the
  template's tag-pinned media URLs need it in the tagged tree, and a docs-only push of its own gets no `main.yml` run, so
  a tag on it is refused. Then wait for `main.yml` on the pushed head and set the tag on that head.
- **Release names**: every minor release is named after a lighthouse. The release commit takes the next
  free name from `docs/release-names.md` and marks it assigned there; the heading is
  `## 0.21.0 "Name" (YYYY-MM-DD)`. Patch releases repeat their minor's name. Tags stay `vX.Y.Z`. The
  GitHub release title is `TasmoFleet X.Y.Z "Name"` (derived from the heading by
  `make changelog-title`), and announcements and forum posts use the same form. Old sections without a
  name stay valid.
- **Patch releases (X.Y.Z with Z>0) never add or change a database migration; a schema change
  always means a new minor version.** The tag build enforces it (`make migration-guard`).
- **Credit outside contributors**: every merged PR by someone else, and every issue or
  report by someone else that led to a change, is credited at the end of that change's
  CHANGELOG line as `(#N, thanks @handle)`. Do not credit the maintainer's own work.
- Tags are signed (`git tag -s vX.Y.Z`) and only set on a green commit of `main`. The tag
  run (`release.yml`) checks that the commit is green already (`required` and `main.yml`, see RELEASE tier; no tests are repeated), and the
  image, the GitHub release and the demo site follow only when that passed.
- **Announce every release** in the one pinned Announcements discussion "TasmoFleet releases" (#315),
  after the tag run has published the image and the GitHub release. Edit its body (`updateDiscussion`):
  the "Current release" section shows `TasmoFleet X.Y.Z "Name"`, the image tags
  (`nofuturekid/tasmofleet:X.Y.Z`, also on ghcr.io), upgrade notes (migrations or "No database
  migration"), a short bullet list of the changes with issue refs and `thanks @handle` credits, and links
  to the GitHub release and `CHANGELOG.md`. A minor release also adds a short comment (3-5 bullets) so
  watchers get a notification; a patch release only edits the body. No per-release discussions. English,
  no fluff.
- **Unraid users run `:latest` from the Community Applications template**
  ([nofuturekid/unraid-templates](https://github.com/nofuturekid/unraid-templates), `templates/tasmofleet.xml`).
  With every release:
  - add the release to the template's `<Changes>` block;
  - edit the first post of the [Unraid support thread](https://forums.unraid.net/topic/201022-support-tasmofleet/)
    (current release line, links, setup notes that are still true). No reply post per release; only a
    release users have to act on (template, port or variable change, a manual upgrade step) also gets a
    reply post, upgrade notes first, because only replies notify the thread's followers;
  - a release that changes ports, variables or anything else in the template ships the template change
    in the same moment the image becomes `:latest`. An existing install keeps its saved template, so such a
    release must also keep existing installs working without edits, or say exactly what to change, at the
    top of the CHANGELOG section, the announcement, the template `<Changes>` and the forum post.
  - **Media linked from any published CA template revision is never deleted from `main`.** The CA feed
    is regenerated on Squid's schedule and can carry an old template revision for days (#423: the 0.24.0
    template still linked two screenshots that the 0.25.0 media refresh had removed). From the next
    release on, the template's screenshots link tag-pinned URLs
    (`https://raw.githubusercontent.com/nofuturekid/tasmofleet/v<X.Y.Z>/docs/media/...`), so later
    media changes cannot break an old feed entry. `docs/media/transaction.png` and
    `docs/media/device-dark.png` stay on `main` for the 0.24.0 revision even though no doc links them.

## Pull requests and the protected main

`main` is protected on GitHub by the ruleset `main`: no force pushes, no deletion, linear
history, signed commits, PR and the status check `required` from `pr.yml`. Every change,
docs-only ones included, goes through a pull request: branch, push, open a PR against `main`,
wait until CI is green on the PR, then the maintainer merges it **fast-forward only** by
pushing the PR head to `main`, so the commits keep their own signatures:

```sh
git fetch origin && git rebase origin/main   # if main moved: rebase, re-sign, push, wait for CI again
git push origin <branch>:main                # ff push of the green PR head; GitHub marks the PR merged
```

Only repository admins may push to `main` (ruleset bypass), and only a PR head whose `required`
check is green. If `main` moved, the branch is rebased (and re-signed), pushed and must be green
again before the fast-forward push; there is no other merge path. Never merge through the GitHub
button: the only method enabled there is rebase, and GitHub's rebase commits are unsigned, so
the ruleset rejects them.
`pr.yml` runs the FAST tier on every PR: a `changes` job detects docs-only PRs (heavy jobs
skipped), PRs that touch a `SAFETY` package (race and diff coverage added) or Go code (revert check added), and the final `required`
job passes only when every job that had to run passed; a skip counts only when the PR did
not ask for that job; the link check, the migration guard and the release section guard must always succeed. No approvals are required (single maintainer). Release tags are still pushed
directly, on a green commit of `main`.

**UI changes:** the agent makes screenshot pairs per screen (mockup and build where a mockup exists,
otherwise before and after; 1280 and 375 px, light and dark) and keeps them outside the repo. During design
phases these local before/after comparisons are what the maintainer looks at; they never hold work back.
Before merging, the coordinator compares them; every visible difference is fixed or listed in the PR with
the reason. Screenshots are never committed to any branch or embedded in a PR. "Tests pass" is not
acceptance for UI work.

## Branches and worktrees

After a pull request is merged into `main`, its branch is deleted on origin and the
local worktree and branch are removed. Before deleting, check containment:
`git cherry origin/main <branch>` shows only `-` lines, or the branch's diff against
`main` is empty (rebased or squashed work). Branches with uncontained changes are never
deleted silently.
