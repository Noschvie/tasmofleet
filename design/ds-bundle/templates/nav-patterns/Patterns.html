Navigation and in-page patterns

Proposal for tasmofleet: top navigation, sub-navigation, page header, row actions, bulk actions, section toggles, links vs buttons, plus the QA v0.9.0 decisions (sections 8–13; screen-level fixes in Screens). Built on styles.css plus patterns.css (new classes listed at its top). Resize below 640px for the phone variants.

1 · Top navigation

Server-rendered details.navgroup. The group that contains the current page is underlined in teal; the current item has aria-current="page" (bold + teal bar). Menus sit on the overlay surface, left-aligned under their trigger; only the user menu aligns right. Every group lists the list page first (Devices, Transactions), then its actions (#75). System is admin only. Sign out is the last item of the user menu. Below 640px: brand + Menu button, one full-width panel with the same groups as sections; every row 44px.

4 · Row actions

At most two direct buttons (above). More than two, or a destructive action among others: one Actions menu in the last cell, right-aligned, vertically centred in the row; on phones it sits at the end of the first line. Links navigate, buttons act, Delete… is last, red, behind a separator, and opens a confirm dialog. Menus in the last rows open upward (.rowmenu.up).

5 · Bulk actions

One bar, fixed to the bottom of the viewport while rows are selected (hidden otherwise): count, Clear selection, then the actions. The page gets bottom padding of --bulkbar-h so nothing ends up under it. Below 60rem the actions collapse into one Actions menu that opens upward; on phones the bar spans the full width and is one row high, so it never covers the table header or the row you are reading. Shown here in place; see Devices and Firmware for the fixed bar.

7 · Links vs buttons

A link changes the page and nothing else. Everything that changes state is a button (in a POST form when it acts directly). Destructive actions are red .danger buttons, end in "…", and are confirmed in a dialog whose confirm button repeats the verb.

8 · Control sizes and alignment

One height per size: default 34px, sm 28px, both 40px on phones. One size per group: page-header actions are default; toolbars and pagers are always sm, auto-width, never stretched. Labels are optically centred (caps trimmed), including label.button, the power toggle, pills and nav tabs. On phones every link that acts as a row or form action gets a 40px hit area (#7 #8 #13).

9 · Table tools and cells

Columns is a plain menu button at the toolbar's right end, without a tooltip; any open menu hides floating tooltips. Its items are wrapping checkbox rows inside the overlay, so long labels never clip (#3). Empty cells read "-" in every table (#51). A list of device names is one link to the filtered list that breaks only between names (#34 #84). No column chooser above tables with fewer than two rows.

10 · Empty states

One pattern, in place of the table: .empty-state with a bold title, one sentence, and the action that fills it (a button when it acts, a link when it navigates). Table controls (Select all, Export, Columns, bulk) are not rendered while the list is empty (#22).

11 · Confirmations

One form everywhere: dialog.dlg (section 7), never the browser's confirm(). Without JS the trigger opens a confirmation page with the same layout (.confirm). The confirm button repeats the verb and the trigger's tone (danger stays danger, primary stays primary); facts are a dl.facts; an acknowledgement checkbox sits left of its label at every width; Cancel is a ghost button-styled link to the page you came from (#23 #55).
